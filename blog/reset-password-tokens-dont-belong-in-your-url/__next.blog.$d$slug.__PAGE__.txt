32:T2daa,<h2>Why you shouldn&#39;t put tokens in a reset password URL</h2>
<p>If you&#39;ve ever built a forgot password journey, you&#39;ve probably built this one:</p>
<ol>
<li>The user enters their email address.</li>
<li>You generate a long random token and email them a link.</li>
<li>They click <code>https://example.com/reset-password?token=8f3a...</code></li>
<li>Your page reads the token from the query string, checks it, and lets them set a new password.</li>
</ol>
<p>It&#39;s simple, it&#39;s everywhere, and it&#39;s the approach described in the <a href="https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html">OWASP Forgot Password Cheat Sheet</a>. Earlier this year I worked on a security fix for exactly this flow, and it changed how I think about it.</p>
<h2>How the token leaked</h2>
<p>Nothing was wrong with how the token was generated. It was random, single use and short lived. The problem was where it lived: <strong>in the URL</strong>.</p>
<p>For years this wasn&#39;t a visible problem, because we were on New Relic. By default, New Relic strips query strings from the URLs it records, perhaps for exactly this reason, so the token never showed up anywhere we looked.</p>
<p>Then we moved to Dynatrace. Like most monitoring tools it does its job very well. It captures page loads, requests and user actions, and every one of those records includes the full URL, query string and all. Overnight, every reset token a customer used started landing in our logs, readable by anyone with access to the dashboards, and potentially allowing anyone with access to these tokens to reset a customer&#39;s password. Nothing in our code had changed. We had just swapped one tool for another with different defaults.</p>
<p>That&#39;s the real lesson here. If your security depends on every tool in the chain having the right default settings, a routine platform migration can quietly undo it.</p>
<p>Once I started looking, the URL turned out to be a pretty leaky place to keep a secret:</p>
<ul>
<li><strong>Observability and RUM tools</strong> record full page URLs, including query strings.</li>
<li><strong>Server and proxy access logs</strong> (load balancers, CDNs, WAFs) log the request line by default.</li>
<li><strong>Browser history</strong> keeps the link, which matters on shared or family devices.</li>
<li><strong>The <code>Referer</code> header</strong> can send the URL to any third party script, font or analytics provider on the page.</li>
<li><strong>Tag managers</strong> such as Google Tag Manager inject marketing and analytics scripts into the page, and every one of those scripts can read the full URL, token included, straight from <code>window.location</code>.</li>
<li><strong>Email link scanners</strong> in corporate mail systems often visit links before the user does, which can use up or expose the token.</li>
<li><strong>Screenshots and screen shares</strong> of a support call happily show the address bar, and are an OCR step away from being compromised.</li>
</ul>
<p>None of these are exotic attacks. They&#39;re just normal parts of how the web works, and each one is another copy of a credential that can take over an account.</p>
<h2>The usual mitigations are band aids</h2>
<p>You can harden the link approach, and OWASP recommends most of these steps if you keep links:</p>
<ul>
<li><strong>Set <code>Referrer-Policy: no-referrer</code> on the reset page.</strong> By default, when a page loads a script, image or font from another site, or the user clicks a link away from it, the browser sends the current page&#39;s URL to that site in the <code>Referer</code> header. On a reset page, that URL contains the token. This response header tells the browser not to send the <code>Referer</code> header at all, so the token stays on your site.</li>
<li><strong>Mask query parameters in your monitoring tool</strong> so tokens are redacted before they&#39;re stored.</li>
<li><strong>Keep expiry short</strong> and <strong>invalidate the token on first use</strong>, so a leaked token is only useful for a small window.</li>
</ul>
<p>The trouble is that every mitigation is opt in, and each new tool, proxy or third party script you add later is another place the URL might get recorded. You&#39;re relying on every system in the chain being configured correctly, forever. Moving the token into the URL fragment (<code>#token=...</code>) keeps it out of server logs, but client side monitoring scripts can still read it.</p>
<p>The more reliable fix is to stop putting the secret in the URL at all.</p>
<h2>The OTP approach</h2>
<p>Instead of emailing a link with a token in it, email the user a <strong>one time passcode</strong> and have them type it into the reset form.</p>
<p>The journey becomes:</p>
<ol>
<li>The user enters their email on <code>/forgot-password</code>.</li>
<li>You generate a short code (6 to 8 digits), store a <strong>hash</strong> of it against the account with an expiry, and email the code.</li>
<li>The user is taken to <code>/reset-password</code>, a plain URL with nothing sensitive in it.</li>
<li>They enter the code and their new password in the form, which is sent as a <code>POST</code> body over HTTPS.</li>
<li>The server checks the code, resets the password and invalidates the code.</li>
</ol>
<p>The code never appears in a URL, so it never ends up in access logs, RUM data, browser history or a <code>Referer</code> header. Email scanners can&#39;t use it up by prefetching a link, because there&#39;s no link to prefetch. You also get a nice user experience bonus: someone can read the email on their phone and type the code on their laptop.</p>
<h2>Doing OTP properly</h2>
<p>A 6 digit code has far less entropy than a 32 byte token, so the security comes from the controls around it rather than the code itself:</p>
<ul>
<li><strong>Generate codes with a cryptographically secure random number generator.</strong> <code>Math.random()</code> in JavaScript and <code>new Random()</code> in .NET are built for speed, not secrecy. They work out each number from an internal state, so anyone who sees enough of their output can predict what comes next. A secure generator draws on the operating system&#39;s entropy source, so its output can&#39;t be predicted. Use <code>RandomNumberGenerator.GetInt32()</code> in .NET, <code>crypto.randomInt()</code> in Node.js, <code>crypto.getRandomValues()</code> in the browser, or the <code>secrets</code> module in Python.</li>
<li><strong>Store only a hash</strong> of the code, just as you would a password.</li>
<li><strong>Keep the expiry short</strong>, 10 to 15 minutes is plenty.</li>
<li><strong>Limit attempts.</strong> After 5 wrong guesses, invalidate the code and make the user request a new one. With 1,000,000 possible codes and 5 attempts, an attacker has a 0.0005% chance.</li>
<li><strong>Rate limit requests</strong> per account and per IP so codes can&#39;t be generated endlessly.</li>
<li><strong>Make codes single use</strong>, and invalidate any previous code when a new one is issued.</li>
<li><strong>Compare in constant time</strong> to avoid timing attacks.</li>
<li><strong>Don&#39;t reveal whether an account exists.</strong> Show the same &quot;if an account exists, we&#39;ve sent a code&quot; message every time.</li>
<li><strong>Once the password has changed,</strong> end existing sessions and send the user a confirmation email.</li>
</ul>

<h2>Wrapping up</h2>
<p>Putting reset tokens in URLs is a recognised pattern, but recognised doesn&#39;t mean risk free. The URL is one of the most copied, logged and shared strings in your whole stack, and any secret you put there will turn up somewhere you didn&#39;t expect. For us, that was our own monitoring platform, the moment we changed vendor. A query string is basically a postcard: it gets where it&#39;s going, but every postie along the way gets a good read of the back.</p>
<p>Switching to an OTP entered on the form keeps the secret out of the URL entirely. You stop relying on every log, proxy and third party script being configured perfectly. Combined with attempt limits, short expiry and hashing, it&#39;s a simpler and safer model, and your customers won&#39;t notice the difference, apart from being better protected.</p>
