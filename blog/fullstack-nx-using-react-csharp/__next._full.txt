14:Tbdea,<h1>Introduction</h1>
<p>Recently, I’ve been using the <a href="https://nx.dev/">Nx</a> monorepo framework quite extensively—but purely for frontend React projects. I’d always thought of Nx as a frontend-focused tool. Turns out, I was wrong (and about two years late to the party).</p>
<p>I recently came across a <a href="https://www.youtube.com/watch?v=8zoR_NpW7io&t=2829s">YouTube video -  Nx + .NET with the nx-dotnet Plugin</a> demonstrating first-class support for .NET applications inside an Nx workspace.</p>
<p>As a full-stack engineer, this genuinely blew my mind. For the first time, it feels possible to build a full-stack architecture that actively prevents one of the most common pain points in web development: broken contracts between frontend and backend. With Nx, API contracts can live in shared libraries with clear ownership, rather than being duplicated, manually synced, or quietly drifting out of alignment.</p>
<p>In this article, I’ll explore what a basic full-stack architecture looks like using Nx, React, and C#, and share what the developer experience is actually like in practice.</p>
<h1>The basic setup</h1>
<p>Nx works on the basic principle of two main folders: <code>apps</code> and <code>libs</code>. For this application, we&#39;ll be using the following folder structure:</p>
<p><strong>apps/</strong></p>
<ul>
<li><code>web/</code> → Next.js frontend application  </li>
<li><code>api/</code> → ASP.NET Core Web API  </li>
<li><code>worker/</code> → .NET background worker (e.g. WebJob, more to show fullstackyness)</li>
</ul>
<p><strong>libs/</strong></p>
<ul>
<li><code>ui/</code> → Shared React UI components  </li>
<li><code>domain/</code> → Shared domain logic  <ul>
<li>Must be framework-agnostic  </li>
<li>Must <strong>not</strong> reference ASP.NET Core, React, or Next.js</li>
</ul>
</li>
<li><code>contracts/</code> → Shared API contracts (DTOs / request &amp; response models)  </li>
<li><code>api-client/</code> → Generated TypeScript client from OpenAPI</li>
</ul>
<h2>Step 1 - Create a mono repo</h2>
<p>Let&#39;s start by creating an empty Nx workspace. Note: this assumes you&#39;ve already set up Nx, Node, .NET, and npm locally.</p>
<pre><code class="hljs language-shell"><span class="code-line"><span class="line-number">1</span><span class="line-content">mkdir fullstack-demo</span></span>

In my case ive gone for React however Nx supports quite a large array of languages and frameworks.</p>

<span class="code-line"><span class="line-number">6</span><span class="line-content">cd ..</span></span></code></pre><p><strong>Why not use Nx generators for .NET?</strong></p>
<p>You might wonder why we&#39;re using manual <code>dotnet</code> commands instead of the <code>@nx-dotnet/core</code> plugin. While Nx does have a .NET plugin, I encountered compatibility issues with the current version of Nx (v22.5.0+). The plugin depends on internal Nx modules that have been refactored or removed in recent versions, causing generation to fail.</p>
<p>By creating .NET projects manually and integrating them through custom <code>project.json</code> files, we get the same benefits:</p>
<ul>
<li>Full Nx integration (build, serve, test commands)</li>
<li>Dependency graph visualization</li>
<li>Affected command support</li>
<li>Task caching</li>
</ul>
<p>This approach is actually more flexible and keeps you in control of the .NET tooling, while still getting all the Nx monorepo benefits. So we don&#39;t really loose much aside from a simpler command to generate a new project. But I guess most people will be accustomed to the dotnet commands anyway.</p>
<p>Once the projects are created we can then create a <code>project.json</code> file for each .NET project to integrate Nx commands with dotnet CLI. The <code>project.json</code> file holds the projects configuration, it also allows Nx to map commands to dotnet which you will see later in the article, as well as control things like project dependencies. </p>

<p>Using Nx to manage a monorepo with .NET and React is a promising combination — the tooling brings solid cross-stack project organisation, making it easier to house both frontend and backend in one workspace. That said, Nx introduces extra complexity that teams will need to invest time in understanding. As the ecosystem matures, improvements to Nx&#39;s generators should help streamline the developer experience further.</p>
<p>Beyond structure and shared contracts, one of the biggest long-term advantages of this setup is how Nx’s affected graph and caching dramatically optimise your workflow. As your monorepo grows, Nx intelligently determines exactly which projects are impacted by a change and only rebuilds or retests those — whether that’s the React frontend, the ASP.NET Core API, or shared domain libraries. Combined with local and remote caching, this significantly reduces CI times, lowers infrastructure costs, and improves developer feedback loops. In a mixed React + .NET environment, this dependency awareness prevents unnecessary rebuilds while still guaranteeing correctness, making the architecture not just scalable in code organisation, but scalable in build performance as well.</p>
<p>Would I use it for a full stack project? I think the answer would be a yes!</p>
